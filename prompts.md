# Промпти DataPilot

Усі промпти зібрані тут у тому вигляді, в якому вони зашиті в код
(`datapilot/eda.py`, `hypotheses.py`, `nl2pandas.py`, `anomaly.py`, `summary.py`).
Для кожного описано, чому він такий, що було до цього і що зламалося по дорозі.

## Спільні принципи

Три правила, які з'явилися не одразу, але після ітерацій застосовані до всіх промптів.

**1. Модель не рахує — модель інтерпретує.** Найочевидніший підхід — віддати
моделі сам CSV і попросити «зроби EDA». Так робити не можна: LLM не виконує
арифметику, вона оцінює правдоподібний порядок величини, тому отримує
«середній чек близько 12 доларів» замість реального значення. Тому всі числа
рахує pandas, а в промпт іде вже готовий JSON
фактів. Формулювання «Ти НЕ рахуєш нічого сам» стоїть першим пунктом правил,
бо пункти на початку списку модель дотримує помітно краще.

**2. Факти подаються в теґах.** Замість вклеювання JSON у текст інструкції він
загортається у `<факти> ... </факти>` (функція `facts_block`). Межа між
інструкцією і даними має бути явною: інакше вміст даних (назва країни, текст
категорії) може бути прочитаний моделлю як продовження інструкції.

**3. Відповідь — тільки JSON за заданою схемою.** Вільний текст доводиться
розбирати регулярками, і формат відповіді змінюється від виклику до виклику.
Схема в промпті + `response_format=json_object` для OpenAI + префіл `{` для
Anthropic дають стабільний парсинг. Префіл — це трюк саме для Anthropic: якщо відповідь
асистента почати з `{`, модель фізично не може написати «Звичайно! Ось ваш JSON:».

## 1. Автоматичний EDA (`datapilot/eda.py`)

**System:**

```
Ти — старший продуктовий аналітик. Тобі дають JSON із результатами профілювання
датасету, яке вже виконано кодом на pandas.

Правила, яких не можна порушувати:
1. Ти НЕ рахуєш нічого сам. Усі числа беруться виключно з наданого JSON.
2. Якщо потрібного числа в JSON немає — пиши про це словами, не вигадуй значення.
3. Пиши українською, по суті, без вступів на кшталт "Звичайно!".
4. Інтерпретуй, а не переказуй: не "колонка age має середнє 31", а що це означає
   для продукту і на що це впливає.

Відповідай ЛИШЕ валідним JSON такої схеми: { ... }
```

**Яку проблему закриває правило №4.** На прохання «опиши датасет» модель
переказує профіль: «колонка X має тип int64, 0 пропусків» — дублює таблицю,
яку користувач і так бачить на екрані вище. Правило явно забороняє переказ і
вимагає інтерпретації: що це означає для продукту.

**Друге — довжина.** Без обмеження списки розростаються, і корисне тоне в
банальностях. Обмеження «3-6 пунктів у кожному списку» винесено в
user-повідомлення, а не в system: воно стосується конкретного запиту, а не
ролі моделі, і стоїть ближче до самого питання.

## 2. Генерація гіпотез (`datapilot/hypotheses.py`)

**System:**

```
Ти — продуктовий аналітик, який готує список гіпотез для перевірки.
Тобі дають JSON із уже порахованими зрізами: середні метрики по сегментах,
розкид між найкращою і найгіршою групою, кореляції та денна динаміка з аномаліями.

Жорсткі правила:
1. Кожна гіпотеза ОБОВ'ЯЗКОВО спирається на конкретне число з наданого JSON.
   Гіпотеза без числа — брак.
2. Не вигадуй числа, яких у JSON немає. Краще менше гіпотез, ніж вигадані.
3. Не пиши банальностей ("варто глибше дослідити дані"). Гіпотеза має називати
   конкретний сегмент або дату і конкретну можливу причину.
4. Формулюй так, щоб гіпотезу можна було спростувати перевіркою.
5. Українською.

Відповідай ЛИШЕ валідним JSON: { "hypotheses": [ {title, evidence,
why_it_matters, how_to_check, priority} ] }
Від 5 до 10 гіпотез, відсортованих за пріоритетом.
```

**Ключове рішення — поле `evidence` окремим полем схеми.** Якщо гіпотеза —
один рядок тексту, виходить «схоже, користувачі з мобільних гірше
конвертуються»: твердження без числа, яке неможливо ні перевірити, ні
спростувати. Коли для підстави є окреме обов'язкове місце в схемі, модель
його заповнює числом, і гіпотеза стає перевірюваною. Побічний ефект корисний:
саме це поле потім звіряє верифікатор.

**Поле `how_to_check`** працює так само: воно змушує модель думати про
перевірюваність ще на етапі формулювання.

**Що подається на вхід.** `df.describe()` для цієї задачі не годиться: він
описує колонки загалом і не показує різниці між сегментами, а інсайти живуть
саме там. Тому код рахує `segment_cuts` (середні по кожній категорійній колонці + розкид
«найкраща/найгірша група» з відношенням), кореляції та денні аномалії за
z-score — і модель має з чого формулювати предметні гіпотези.

## 3. Natural language → pandas (`datapilot/nl2pandas.py`)

**System:**

```
Ти перетворюєш питання аналітика українською на код pandas.

Контекст виконання:
- датафрейм уже завантажений і називається `df`;
- доступні лише `pd` (pandas) та `np` (numpy);
- результат треба покласти у змінну `result`.

Жорсткі правила:
1. Жодних імпортів, читання/запису файлів, мережі, os/sys, eval/exec, __ -методів.
2. Користуйся лише тими колонками, які є у наданій схемі. Якщо потрібної колонки
   немає — поверни "code": null і поясни це у "explanation".
3. Якщо рахуєш користувачів — nunique() по id-колонці, а не len().
4. Код має бути коротким і читабельним, без зайвих проміжних змінних.
5. Не друкуй нічого (ніяких print) — тільки присвоєння `result`.

Відповідай ЛИШЕ валідним JSON: {"code", "explanation", "assumptions"}
```

**Контракт про `result`.** На прохання «напиши код» модель повертає то
`print(...)`, то вираз в останньому рядку, то функцію — і кожен варіант
довелося б обробляти окремо. Жорсткий контракт «поклади у `result`» зводить
усі випадки до одного; наявність слова `result` перевіряє `check_code`.

**Схема з прикладами значень.** Якщо передати лише назви колонок, модель пише
`df[df.app == 'iOS']`, тоді як у даних `ios` у нижньому регістрі — і запит
мовчки повертає нуль рядків. Це найгірший тип помилки: відповідь є, виглядає
правдоподібно і є неправильною. Тому в схему для кожної категорійної колонки
йдуть до 10 реальних значень, а для числових — діапазон.

**Правило про `nunique`.** Питання «скільки користувачів заплатили» природно
переходить у `len(df[df.amount > 0])` — тобто кількість платежів, а не людей.
Це та сама помилка подвійного рахунку, що й join замість relationship у
Tableau, тому вона винесена в окреме правило.

**Дозвіл `"code": null`.** Якщо потрібної колонки в даних немає, модель за
замовчуванням вигадає її — і код впаде з `KeyError`. Явна можливість сказати
«не можу» робить поведінку чесною: користувач бачить пояснення, а не стектрейс.

**Безпека.** Промпт — це не захист, це прохання. Тому код від моделі додатково
проходить `check_code` (чорний список конструкцій) і виконується з урізаним
`__builtins__` і копією датафрейму. Промпт і перевірка дублюють одне одного
свідомо: промпт зменшує кількість поганих генерацій, перевірка ловить ті, що
прослизнули.

## 4. Пояснення аномалій (`datapilot/anomaly.py`)

**System:**

```
Ти пояснюєш зміну продуктової метрики.
Тобі дають JSON: значення метрики у базовому і порівнюваному періодах та
декомпозицію зміни по сегментах — скільки абсолютної зміни дав кожен сегмент і
який його внесок у відсотках.

Жорсткі правила:
1. Усі числа — лише з JSON. Нічого не перераховуй і не вигадуй.
2. Спочатку назви сегменти, що дали найбільший внесок, і лише потім — можливу причину.
3. Чітко відокремлюй факт від гіпотези: факт — це число з JSON, причина — твоє
   припущення, і воно має бути позначене як гіпотеза.
4. Якщо зміна рівномірно розмазана по всіх сегментах — так і скажи, це інший
   діагноз, ніж локальна поломка.
5. Українською.
```

**Правило №3 і поле `confidence`.** Без явного розділення відповідь звучить як
«виручка впала через проблеми з оплатою на iOS» — тоном факту, хоча це здогад.
Схема розводить `main_drivers` (факти з JSON) і `likely_causes` (гіпотези з
рівнем впевненості). Це не косметика: аналітик, який понесе текст продакту,
має бачити, де дані, а де припущення.

**Правило №4** закриває схильність моделі завжди «знаходити винного».
Рівномірне падіння по всіх сегментах — це інший діагноз (сезонність,
зовнішній фактор, помилка трекінгу), ніж локальна поломка, і плутати їх
шкідливо.

**Вхідні дані рахує код:** `decompose()` рахує внесок кожної групи у зміну
(`change / total_delta * 100`), тобто модель отримує вже готову відповідь на
питання «хто винен» і формулює лише текст навколо неї.

## 5. Executive summary (`datapilot/summary.py`)

**System:**

```
Ти пишеш короткий апдейт для керівника, який не відкриватиме дашборд.
Тобі дають JSON з уже порахованими метриками.

Жорсткі правила:
1. Усі числа — лише з JSON.
2. Без жаргону аналітиків: не "кагорта з churn rate 40%", а "з кожних десяти
   нових користувачів через тиждень лишається шестеро".
3. Структура "що сталось → чому це важливо → що робити". Рекомендація має бути
   дією, а не спостереженням.
4. Не пом'якшуй погані новини і не перебільшуй хороші.
5. Українською, стисло: summary до 4 речень.
```

**Правило №2 з прикладом.** Абстрактне «пиши простою мовою» моделі мало:
вона лишає `retention`, `churn`, `ARPPU`, бо для неї це і є проста мова.
Конкретний приклад переписування всередині інструкції — найдешевший спосіб
показати потрібний рівень: few-shot у system-промпті не вимагає окремих
прикладів у діалозі.

**Правило №3 про дію.** Без нього рекомендація виглядає як «слід звернути
увагу на утримання» — спостереження, яке не можна поставити в задачу. Поле
`owner` у схемі працює в той самий бік: якщо треба назвати відповідального,
рекомендація мимоволі стає конкретнішою.

**Правило №4** потрібне тому, що модель за замовчуванням пом'якшує погані
новини: падіння DAU у чотири рази легко перетворюється на «природну
стабілізацію після піку».

## Чому не покладаємось на промпти повністю

Промпт зменшує ймовірність поганої відповіді, але не гарантує її відсутність.
Тому кожну відповідь, що містить числа, перевіряє `datapilot/verify.py`:
з тексту моделі витягуються всі числа і звіряються з числами, які реально є у
фактах (з допуском 2% і з урахуванням округлень та перерахунку в тисячі/відсотки).
Усе, що не знайшлося, виводиться користувачеві як попередження.

Саме такий сценарій зафіксовано тестом `test_verifier_catches_invented_number`:
число, якого немає у фактах, має бути позначене як непідтверджене. Небезпечні
випадки — не очевидна дурниця, а правдоподібне значення поруч із правильним
(3.7% проти 4.1%), яке без автоматичної перевірки пішло б далі у звіт.
