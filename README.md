# DataPilot — AI-асистент продуктового аналітика

Лабораторна робота №4, курс «Методи та засоби продуктової аналітики».
Соломка Андрій, група ІМ-31.

DataPilot — це CLI-інструмент, який забирає на себе рутинну частину роботи
аналітика: профілювання нового датасету, пошук сегментів, що поводяться
інакше, відповіді на разові питання по даних і підготовку тексту для
стейкхолдера. Усі числа рахує pandas, а LLM відповідає лише за інтерпретацію
та формулювання. Кожне число, яке модель назвала у своїй відповіді,
автоматично звіряється з фактами — те, чого в даних немає, позначається як
непідтверджене прямо у виводі.

## Реалізовані функції

| Команда | Що робить | Пункт завдання |
|---|---|---|
| `eda` | Профілює CSV: типи, пропуски, викиди за IQR, дублікати, прапорці якості даних; LLM пише інтерпретацію | 1 |
| `hypotheses` | Рахує зрізи по сегментах, кореляції та денні аномалії, LLM формулює 5–10 перевірюваних гіпотез із числами | 2 |
| `ask` | Питання природною мовою → код pandas → виконання в пісочниці → результат; код завжди показується | 3 |
| `explain` | Декомпозиція зміни метрики між двома періодами по сегментах + гіпотеза причини | 4 |
| `summary` | Executive summary для керівника з JSON-метрик | 5 |

Додатково (пункт 6): **верифікатор чисел** `datapilot/verify.py` — витягує всі
числа з відповіді моделі та звіряє їх із фактами з допуском 2%, враховуючи
округлення й перерахунок у тисячі та відсотки.

## Швидкий старт

```bash
git clone https://github.com/AndriiSolomka/kpi-product-analytics-lab4.git
```

### Яку модель підключити

За замовчуванням DataPilot працює з **локальною моделлю** — без ключів і без
оплати. Код однаковий для всіх варіантів, міняється лише `.env`.

**LM Studio (основний варіант, на ньому знято всі демо).** Модель —
Gemma 4 E4B (`gemma-4-e4b-it-mlx`, 4-bit, ~7 ГБ):

```bash
brew install --cask lm-studio           # або інсталятор з lmstudio.ai
lms get google/gemma-4-e4b --mlx
lms load gemma-4-e4b-it-mlx --context-length 16384
lms server start                        # http://localhost:1234/v1
```

```ini
# .env (можна не створювати — сервер знайдеться сам)
DATAPILOT_PROVIDER=lmstudio
DATAPILOT_MODEL=gemma-4-e4b-it-mlx
```

**Ollama:** `ollama pull llama3.1`, у `.env` `DATAPILOT_PROVIDER=ollama` і
`DATAPILOT_MODEL=llama3.1` (адреса `http://localhost:11434/v1` підставляється
сама). Для llama.cpp, vLLM чи іншого OpenAI-сумісного сервера —
`DATAPILOT_BASE_URL=http://localhost:ПОРТ/v1`.

Якщо в `.env` нічого не задано, інструмент сам шукає запущений сервер: спершу
LM Studio (порт 1234), потім Ollama (11434). Частина локальних збірок не
приймає строгий JSON-режим, тому запит автоматично повторюється без нього, а
JSON витягується з тексту відповіді.

**Хмарні моделі (необов'язково).** Anthropic: `ANTHROPIC_API_KEY=sk-ant-...`;
OpenAI: `OPENAI_API_KEY=sk-...` і `DATAPILOT_PROVIDER=openai`.

> Мала локальна модель слабша за хмарну у формулюваннях, але для цього
> інструменту це менш критично: числа вона не рахує, а все, що назве,
> перевіряється верифікатором проти фактів. Під неї довелося посилити два
> промпти — див. розділ «Прогін на локальній моделі».

**Без моделі інструмент теж запускається.** Прапорець `--no-llm` виконує лише
детерміновану частину (усі розрахунки й таблиці), а якщо локального сервера
немає і ключ не задано — вмикається режим `mock` із заглушками (для тестів і CI).

### 3. Питання природною мовою

```bash
python -m datapilot ask data/payments.csv "Покажи топ-10 країн за виручкою"
```

Інструмент показує згенерований код, пояснення, припущення — і лише потім
результат, щоб аналітик міг перевірити логіку, а не довіряти чорній скриньці.

### 4. Гіпотези та executive summary

```bash
python -m datapilot hypotheses data/users.csv --json demo/hypotheses.json
python -m datapilot summary demo/metrics.json --audience "CEO"
```

Якщо модель назве число, якого немає у фактах, воно буде позначене:

```

```

## Прогін на локальній моделі

Усі команди прогнано на Gemma 4 E4B у LM Studio (MacBook Pro, Apple Silicon);
повні виводи — у [`demo/outputs/local/`](demo/outputs/local/). Одна команда
триває 20–60 с.

`explain` — окрім головного драйвера, модель окремо вказала на падіння iOS і Android:

```

Метрика нових користувачів зросла на 313.87% в порівнятному періоді, що майже повністю зумовлене мобільними додатками.

Головні драйвери
 • Сегмент 'mobile' (за типом додатку) згенерував найбільший абсолютний ріст (+94013.0) та внесок (+110.1%).
 • Сегмент 'United States of America' (за країною) згенерував найбільший абсолютний ріст (+16748.0) та внесок (+19.61%).

Можливі причини (гіпотези)
 • [medium] Експлуатація успішної кампанії або вихідний сплеск у мобільному сегменті, який був значно потужнішим порівняно з базовим періодом.
   Мобільний сегмент показав зростання на 549.91% (з 17096.0 до 111109.0).

Що перевірити далі
 • Аналізувати які саме дії чи канали привели до такого потужного зростання в сегменті 'mobile'.
 • Звернути увагу на падіння у сегментах 'ios' (-98.98%) та 'android' (-89.81%), щоб зрозуміти, чи це технічні проблеми або зміна поведінки користувачів.
 • Проаналізувати, чи є зростання в мобільних додатках репрезентативним для загального тренду, чи це ізольований ефект.

✔ Перевірка чисел: усі 8 числа з тексту знайдено у фактах.
```

`ask` — згенерований код:

```
result = df.groupby('country_name')['amount_usd'].sum().nlargest(10)
```

Що довелося змінити під малу модель:

| Проблема на Gemma 4 E4B | Що зроблено |
|---|---|
| `eda`: середню тривалість сесії з колонки `avg_session_min` назвала секундами, а виручку `revenue_usd` — євро | у промпт EDA додано правило: одиниці беруться з назви колонки (`_min`, `_usd`, `_cnt`) |
| `eda`: згадала «коефіцієнт відмов», якого немає в даних | правило: не згадувати метрик, яких немає в JSON |
| `explain`: назвала лише сегменти зі зростанням і пропустила падіння iOS; частину тексту написала англійською | правило: окремо називати сегменти з падінням; усі поля — українською |
| верифікатор позначав «падіння на 98.98%» як вигадане, бо у фактах −98.98 | числа звіряються за модулем: знак модель передає словами |

## Як це влаштовано

```
datapilot/
  llm.py          шар доступу до LLM: LM Studio / Ollama / Anthropic / OpenAI / mock
  profiling.py    детерміноване профілювання, прапорці якості даних
  insights.py     зрізи по сегментах, кореляції, денні аномалії за z-score
  eda.py          функція 1
  hypotheses.py   функція 2
  nl2pandas.py    функція 3 + пісочниця для згенерованого коду
  anomaly.py      функція 4 (декомпозиція внесків сегментів)
  summary.py      функція 5
  verify.py       звірка чисел з відповіді моделі з фактами
  cli.py          інтерфейс командного рядка
```

Принцип усюди однаковий: **код рахує → модель пояснює → код перевіряє**.
Модель ніколи не отримує сирий CSV і ніколи не рахує сама; вона бачить лише
JSON із готовими фактами. Деталі промптів і міркування за ними — у
[`prompts.md`](prompts.md).

### Безпека згенерованого коду

Код від LLM не виконується як є. Перед запуском `check_code` відхиляє імпорти,
роботу з файлами й мережею, `eval`/`exec` і доступ до dunder-атрибутів, а
виконання йде з урізаним `__builtins__` і на копії датафрейму, тому вихідні
дані змінити неможливо. Промпт і перевірка дублюють одне одного свідомо:
промпт зменшує кількість поганих генерацій, перевірка ловить ті, що прослизнули.

## Тести

```bash
python -m pytest tests -q
```

Тести перевіряють саме ризиковані місця: що верифікатор ловить вигадане число
й не чіпає округлене, що пісочниця відхиляє небезпечний код і не змінює
вихідний датафрейм, і що декомпозиція знаходить обвал iOS у демо-даних.

## Технології

Python 3.11+, pandas, numpy, pytest; `anthropic` / `openai` SDK для доступу до
моделі; стандартний `argparse` для CLI — без зайвих залежностей.
